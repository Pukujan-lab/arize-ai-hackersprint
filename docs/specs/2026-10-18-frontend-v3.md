**Status:** owner-approved

This document is the build spec. It states outcomes only: what the app must do, what must be true of it, and how each claim is verified. It does not name a framework, library, build tool or dependency policy. The builder chooses the implementation and owns `web/`.

The owner's statements are the authority. Agent-authored notes — resume documents, handoffs, build logs, `.oio/drafts/*`, PR bodies and issue comments written by agents — are evidence, never policy. Where this spec and an agent note disagree, this spec wins.

## Why this exists

The current frontend is seven standalone pages with no component layer. That produced three independent failure modes, each observed in production:

1. Every change had to be applied in several places, and the copies drifted.
2. A requirement could change meaning between the issue, the test and the builder prompt. The speaker control was removed by a written rule the owner says they never asked for; tour controls were drawn over the memo on phones because a test asserted they belonged there.
3. Retiring a page meant deleting a menu link. The route and the file stayed, so "archived" pages kept answering — including the old map at a direct file address.

Regenerating fixes the first. The outcomes and CI checks below exist to fix the second and third.

## Scope

**Kept:** the backend API, the Octo schema and migrations, the voice provider chain, the memo generation, the saved runs.

**Rebuilt:** the frontend, including the 3D county map and its tour.

**Deleted at cutover:** the `/v1`, `/v2`, `/dashboard` and `/guide` pages (their addresses forward, per D1), the entire `static/` page set, the old map and tour code, and every asset only they used.

**Surviving addresses:** `/` (Home), `/map` (Home with the map pane open), `/observability`, `/slides`.

## Owner decisions

- **D1 — Old addresses forward.** `/v1` and `/v2` permanently forward to `/`; `/dashboard` to `/observability`; `/guide` to `/slides`. No old page or file survives.
- **D2 — `/map` stays.** It opens Home with the map pane selected. It is the only legacy address with product meaning and it is linked from the README.
- **D3 — One Listen control**, in the memo header, driving both memo narration and tour narration. There is no second speaker control in the tour bar.
- **D4 — Sources still link out.** Case links and citation cards on the map are dropped, but the Sources panel links to the original court documents.
- **D5 — The frontend is built on the machine that serves the site**, from the exact commit being deployed, before the live site is touched. A failed build leaves the running site untouched. CI runs the same build so a broken build fails the pull request.
- **D6 — Map rewrite, not wrapper.** Keep 3D counties, the guided tour with narration, the basemap and the legend. Drop case links and citation cards.
- **D7 — One version at a time.** The current version is tagged and deleted at cutover. No preview route, no fallback copy, no version directory.
- **D8 — No stack prescription.** No issue, spec, prompt prefix, handoff or contract tells the builder what technology to use.
- **D9 — The assistant writes issues, specs, docs and CI. The builder writes app code only.**

## Map parity

A rewrite is only acceptable if it preserves behaviour. Before any old file is deleted, a dump tool records the current map's behaviour for one real saved run:

`tests/fixtures/run-parity.json` — a saved run with citations, links, question and answer.
`tests/fixtures/tour_parity.json` — stop order, stop text, pin groups, county counts, arc counts and link locations, produced by `tools/parity_dump.py` against the current `/map`.

The new map must reproduce every value in `tour_parity.json` within the stated tolerance, and pass the 20-item behaviour checklist in `docs/specs/2026-10-18-frontend-v3-parity.md`. Pixel similarity is not required; behaviour is.

The parity dump is the last action that needs the old map alive. If it cannot be captured, the rewrite does not start.

## Verification contract

The map exposes a debug object at `window.__precedentMap.v1` so behaviour can be asserted without reading pixels:

```
ready: boolean
state(): { camera, pane, tour, theme, focus, level, focusCounty, label, scene }
    # level: national | state | county | court
    # label: the focused county or court's name, else null
    # scene: { mode: "3d" | "flat", stateMeshes, countyMeshes, coloradoRaised }
setCites(cites, edges, ctx)
order(): number[]
explainText(i): { title, court, year, holding, citedBy, memoLine }
focus(i) / tour(n) / stopTour() / resetCamera()
zoomToCounty(name) / zoomToCourt(i) / zoomOutLevel()
countyScreen(name): { x, y } | null      # the county's centre in canvas coordinates
pinScreen(i): { x, y } | null            # the pin for citation i in canvas coordinates
pinCites(i): number[]                    # the citation indices the pin for citation i stands for
hoverCounty(name | null)
tooltip(): string | null
pinCount, countyCount, countyMeshCount, stateMeshCount, arcCounts
pins(): { key, cat, count }[]        # one entry per pin group; pinCount is its length
countyHeat(): Record<string, number>
summary(): string
```

`countyMeshCount` and `stateMeshCount` are the number of county and state polygons drawn, so O17 can be
asserted without reading pixels.

`pins()`, `countyHeat()` and `summary()` exist so a rewrite can be compared with the golden capture in `tests/fixtures/`.

This is a product-internal interface for tests. It is not a public API and carries no security promise.

## CI invariants

Each one is a short assertion. Each corresponds to a failure that shipped green.

| Invariant | Check |
|---|---|
| One navigation source per page | one nav landmark; its links equal the four surviving addresses |
| No link to a retired address | crawl every page for `/v1`, `/v2`, `/dashboard`, `/guide`, `/static/*.html` |
| No retired address returns a page | request every retired path and every old filename; accept only 404 or a redirect to a survivor |
| No shared mutable asset between versions | the old frontend folder does not exist; built assets are content-hashed |
| No covered interactive element | `covered()` over 4 pages × 5 widths × 2 themes with a memo and a running tour |
| No horizontal overflow, small targets or tiny text | the three existing helpers, wired into the same sweep |
| No dead code | `vulture app tests tools --min-confidence 80` |
| Build reproducibility | the same build runs in CI and on the deploy host, from a frozen lockfile |
| Per-route metadata in initial HTML | four unique titles, descriptions and canonicals |
| Spec traceability | `tools/spec_policy.py`: every outcome has a test, every test cites a known outcome, the spec is approved, and no stack-prescription phrase appears |

## Rollback

- A build failure happens before the live site is touched, so the running site is unaffected.
- A failed health check restores the previous commit and the previous built artifact.
- The current frontend is preserved as a tag until the owner retires it.
- A revert merge reaches production within minutes of the deploy cycle.
